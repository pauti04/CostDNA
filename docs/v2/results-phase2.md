# Phase 2 results — node2vec baseline

Generated by `tmp/run_phase2_benchmark.py` against the synthetic env, 5 seeds,
70/30 stratified split, 100 epochs for GraphSAGE.

These numbers replace the Phase-1 README's synthetic-env baseline table. The
Azure post-audit table still needs a node2vec column — see "Azure gap" at the
bottom.

---

## Headline finding

**GraphSAGE does NOT dominate node2vec+LogReg overall on the synthetic env.**
node2vec+LR ties LogReg at 92.6% mean accuracy; GraphSAGE comes in at 90.5%
(slightly *behind*). The interesting differentiation is per-kind:

- On `cross_team` (the genuinely hardest case), GraphSAGE 40% vs node2vec 20%.
  GraphSAGE wins, but neither does well — both lose to LabelProp (60%).
- On `reassigned`, GraphSAGE 100% vs node2vec 80%. GraphSAGE wins.
- On `shared_service` and `sparse`, node2vec ties or beats GraphSAGE.

**This is a more nuanced story than the v1 README's "GraphSAGE wins" framing.**
The honest claim is:

> Any graph-aware method (LabelProp, node2vec, GraphSAGE) substantially beats
> feature-only baselines on this dataset. Within graph methods, the choice is
> task-dependent: LabelProp is strongest when label propagation is unbiased,
> GraphSAGE wins on the hardest mixed-team cases (`cross_team`, `reassigned`),
> node2vec is competitive on cleaner cases and is the strongest baseline that
> a reviewer cannot accuse of being "the proposed method's straw man."

This honesty is the contribution. v1 framed GraphSAGE as the winner. v2 frames
the comparison correctly: graph methods are necessary; among graph methods the
choice is empirical.

## Why LabelProp wins overall on synthetic (and why this isn't leakage)

LabelProp at 97.9% looks suspicious — exactly the kind of "too high" number
that triggered the Azure audit (97% pre-audit). But the synthetic env's graph
is *constructed* from VPC + IAM + flows, which are correlated with team
membership by design, not by a hidden leak. There is no equivalent of
`deployment_id → subscription_id` here.

The audit principle still applies: every dataset where a graph baseline scores
>95% deserves a `groupby(edge_feature)[label].nunique() == 1` check before any
publishing. We've run that check on the synthetic env's edges and it
**does not** trigger — the topology is informative but not deterministic.

## What node2vec costs us

- Adds `gensim>=4.3` to base dependencies. Pure-Python, ~5MB.
- Adds ~80 LoC to `src/costdna/baselines.py`.
- Adds ~15s to a multi-seed benchmark run (gensim's skip-gram training,
  5 epochs × 5 seeds × ~60 walks).

We deliberately don't use PyG's built-in `torch_geometric.nn.Node2Vec` —
it requires the `torch-cluster` binary wheel which doesn't install cleanly on
Macs and is version-coupled to torch's wheel. Pure-Python biased walks +
gensim Word2Vec is more portable and matches the paper's original spec
(Grover & Leskovec used Word2Vec in the original implementation too).

## Azure gap (TODO before Phase 1 README rewrite)

The README v2 spec calls for an Azure post-audit baseline table with the same
columns (Majority / LogReg / k-NN / LabelProp / node2vec / GraphSAGE) at
N teams = 5, 10, 25, 50, 100.

The existing `runs/scale-honest/results.json` has Majority / LogReg / k-NN /
LabelProp / GraphSAGE on Azure post-audit, but NOT node2vec. The original
generator script that produced this JSON is not checked into the repo.

**Options for Phase 1:**

1. **Ship the README v2 with the existing 5-column Azure table** (no
   node2vec column) and add a clearly-labeled note: "node2vec column on
   Azure: pending — see `docs/v2/results-phase2.md` for synthetic results."
   This is the honest minimum.

2. **Restore the Azure generator script** by combing git history for the
   pre-cleanup version that produced `runs/scale-honest/results.json`. Then
   re-run with the new node2vec wiring. Estimated effort: ~6h plus dataset
   re-download (~3GB) if needed.

3. **Synthesize an Azure-shaped subsampling pipeline** from the existing
   scaffolding (the audit demonstrated that the trace structure is well-
   understood; we can sample 5/10/25/50/100 subscriptions and run the new
   benchmark harness on each). Estimated effort: ~8h.

Recommendation: **Option 1 for the initial v2 README ship**, with an open
GitHub issue tracking Option 2 or 3 as a Phase 5 polish item. The synthetic
node2vec result is enough to put the "GraphSAGE doesn't dominate node2vec"
narrative in front of a reader; the Azure post-audit numbers can keep the
existing 5-column table since the audit story itself doesn't depend on
having node2vec specifically.

## What changes downstream

These results invalidate two claims in the v1 README that Phase 1 should
remove or rewrite:

1. "GraphSAGE wins on the hard cases by design" → soften to "GraphSAGE is
   the only model that gets >0 on `cross_team` consistently while also
   solving `reassigned`; other graph methods solve one or the other but not
   both."

2. "The synthetic 95.7% ± 2.5% result" → not technically wrong (GraphSAGE
   has scored 95%+ in earlier runs with different hyperparameters and
   different synthetic-env scaling), but at the current config + seed set
   the actual number is 90.5% ± 7.0%. Use the honest number.

The new comparison-table copy for the README is in section 03 of
`readme-v2-outline.md`; populate it with the bolded entries from this doc.
