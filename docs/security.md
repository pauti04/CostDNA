# Security model

This document is the deep version of `SECURITY.md`. It exists so a
security engineer evaluating CostDNA for a pilot can decide in 10
minutes whether the threat model is acceptable.

If you're an end user, the short version is in `SECURITY.md` and on
the landing page at [cost-dna.vercel.app/#security](https://cost-dna.vercel.app/#security).

---

## TL;DR

- CostDNA needs **read-only** AWS permissions to do its job. The
  write-back step (`costdna apply --apply`) is a separate, explicit
  grant gated behind dry-run by default.
- The self-hosted CLI runs **entirely in your environment**. Nothing
  leaves your account, no telemetry, no upstream call to a CostDNA
  server.
- The web demo at `cost-dna.vercel.app/your-account` parses your CUR
  CSV **client-side via PapaParse**. Zero bytes uploaded. Verifiable
  in your browser's Network tab.
- The optional natural-language interface routes through OpenAI's
  API. **Not enabled by default.** If you turn it on, OpenAI sees the
  query and the relevant scan output.

---

## Threat model — what we protect against

The threats CostDNA is designed to mitigate:

| Threat | Mitigation |
|---|---|
| Accidental privilege escalation via inferred-tag write-back | Default `--dry-run`; explicit `--apply` flag; per-resource-type IAM scope; confidence threshold cutoff (no writes below 0.7) |
| Leaking cost / IAM data to a third party (us) | Self-hosted by default; zero outbound network calls from the CLI; no telemetry |
| Tampering with predictions | All inference is deterministic and offline; the same scan output is reproducible bit-for-bit; the `predictions.csv` is human-readable |
| Supply-chain attack via a compromised package | PyPI release pinned via SHA-256 in changelog; Docker image is multi-stage and reproducible from a public Dockerfile; Sigstore signing planned |
| Hostile CSV upload to the in-browser path | PapaParse is the only parser touched; no server-side processing; 5 MB cap enforced client-side |
| Stale or wrong IAM policy in the docs | The IAM JSON is generated by the same code that scans, so they can't drift |

The threats CostDNA does **not** address:

| Threat | Why not |
|---|---|
| Already-compromised AWS credentials | Out of scope — CostDNA inherits whatever access its principal has |
| A malicious customer running CostDNA against an account they don't own | CostDNA is a tool; access control is AWS's problem |
| OpenAI prompt-injection in the optional NL interface | The interface returns text and tool calls; tool results are pure data lookups, not arbitrary execution |
| Side-channel info disclosure via timing of API calls | Out of practical scope at this project size |

## IAM scope — read-only path

For `costdna scan` (the primary use case):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CostDNAReadOnly",
      "Effect": "Allow",
      "Action": [
        "cloudtrail:LookupEvents",
        "ec2:DescribeInstances",
        "ec2:DescribeVolumes",
        "ec2:DescribeVpcs",
        "ec2:DescribeSubnets",
        "ec2:DescribeFlowLogs",
        "rds:DescribeDBInstances",
        "lambda:ListFunctions",
        "s3:ListAllMyBuckets",
        "s3:GetBucketTagging",
        "iam:ListRoles",
        "iam:ListUsers",
        "iam:GetRole",
        "iam:GetUser",
        "iam:ListAttachedRolePolicies",
        "ce:GetCostAndUsage",
        "ce:GetCostAndUsageWithResources",
        "ce:GetCostCategories"
      ],
      "Resource": "*"
    }
  ]
}
```

This is the entire permission set. Deploy it in one command (CloudFormation or Terraform, read-only by default) — see [`deploy/`](../deploy/). No `*:*`, no `iam:Pass*`, no
write actions. If you have a finer-grained policy in your org
(e.g. resource ARNs scoped to specific accounts), restrict
`Resource: *` accordingly — CostDNA only needs to read what's in
the target account.

## IAM scope — write-back path (opt in)

For `costdna apply --apply` (writes the inferred tags back to AWS):

```json
{
  "Sid": "CostDNATagWriteback",
  "Effect": "Allow",
  "Action": [
    "ec2:CreateTags",
    "rds:AddTagsToResource",
    "lambda:TagResource",
    "s3:PutBucketTagging"
  ],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "aws:ResourceTag/managed_by": "costdna"
    }
  }
}
```

Notes:

1. We recommend scoping the `Resource` to specific account IDs or
   resource-prefix patterns.
2. The `aws:ResourceTag/managed_by` condition means we will only
   ever modify tags on resources that already have the
   `managed_by=costdna` marker. Bootstrap by tagging once manually
   on a single resource; CostDNA can then expand from there.
3. The default `costdna apply` runs in **dry-run mode** and prints
   the `aws ec2 create-tags ...` commands instead of executing them.
   `--apply` is the explicit consent to actually write.
4. CostDNA never writes a tag for a prediction below confidence
   0.7 (the same threshold the in-CLI report flags as
   "needs human review").

## Network model

| Path | Outbound calls |
|---|---|
| `costdna scan --aws-profile prod` | AWS APIs (boto3 over HTTPS, IAM role of the profile) — that's it |
| `costdna scan --cloud azure` | Azure Management APIs (the typed SDK over HTTPS) |
| `costdna scan --cloud gcp` | GCP APIs (google-cloud-* over HTTPS) |
| `costdna scan --synthetic` | None — runs offline |
| `costdna ask "..."` (with `[agent]` extras) | OpenAI API — opt-in only |
| `cost-dna.vercel.app/your-account` (browser) | None — pure client-side PapaParse |
| `cost-dna.vercel.app/api/ask` (live demo) | OpenAI API (rate-limited, $5/day cap) |

The CostDNA project does not run any backend that receives customer
data. The Vercel-hosted demo is on a synthetic 68-resource dataset
that ships with the repo; we don't see your data.

## Supply chain

| Artifact | Provenance |
|---|---|
| PyPI package | Built from a tag on `github.com/pauti04/CostDNA` via GitHub Actions. SHA-256 in `CHANGELOG.md` per release. |
| Docker image (`pauti04/costdna:*`) | Multi-stage build from the public Dockerfile. Multi-arch (amd64 + arm64). Built via the same GHA workflow. |
| Sentence-transformer weights | `sentence-transformers/all-MiniLM-L6-v2` from Hugging Face. The pinned commit hash is in `pyproject.toml`. |
| node2vec embeddings | Computed on-device via gensim. No external service. |

Sigstore signing for PyPI releases is on the roadmap — when it
lands, `pip install` will be verifiable end-to-end. Today, the
verification path is the GHA provenance manifest plus the SHA-256
in the release notes.

## Data residency

- **Self-hosted:** all data stays in the customer's AWS account. The
  CLI writes outputs to a local directory the customer specifies.
  No data crosses an org boundary.
- **In-browser scan:** all parsing happens in the visitor's browser.
  No upload, no server-side processing.
- **Managed scan (invite-only):** customer creates a read-only IAM
  role; we assume it from a serverless region the customer chooses
  (us-east-1, eu-west-1, ap-southeast-2 supported). The scan output
  is computed in that region and emailed back as a single PDF +
  attached predictions.csv. No long-term retention beyond 14 days.

## GDPR

Cloud bills do not contain PII in the GDPR sense — they contain
resource ARNs, dollar amounts, timestamps. IAM principals
(`alice.smith@company.com`) can be PII if the email is in the role
name. Two mitigations:

1. CostDNA never logs or persists IAM principals beyond the
   in-memory scan; the predictions.csv contains aggregate
   per-team rollups, not per-user data.
2. The optional `--anonymize-principals` flag (planned, tracked
   in `docs/limitations.md` §4) hashes IAM-user names before they
   enter feature extraction.

## SOC 2

- **Self-hosted CostDNA:** the relevant attestation is the
  customer's own — CostDNA runs entirely inside their security
  boundary, inheriting whatever controls they've already attested.
- **Managed scan:** does not exist today. If it were built, SOC 2 Type I would be a prerequisite; it is
  progress. Target: pre-GA of the managed tier.
- **Type II:** planned post-pilot, contingent on at least one paying
  enterprise customer to justify the audit cost.

## Audit trail

Every CostDNA operation logs:

- Timestamp + invoking principal (from the CLI's AWS profile)
- Commands run (`scan`, `apply`, `learn`, etc.)
- For `apply` runs: which resources got which tags
- For dry-run: the equivalent commands that would have been written

Logs are written to the directory specified by `--save-dir` and
are plain JSONL. No PII, no IAM credentials, no cost data —
just operation metadata.
